## Core Model

An OpenMusic server consists of:

- Songs
- Albums
- Artists
- Playlists
- Stations

Most responses follow the same structure:

- `data` wrapper
- `id` and `type`
- `attributes` for details
- `relationships` for linked resources

This lets clients work with different resource types in a predictable way.

Relationships are optional, if it is omitted, no relationships were included in that resource payload.
If a relationship key is present with an empty array, it means the relationship was included and no related resources were found.

## Capabilities

Clients should not assume every endpoint is available.
Instead, they should call the info endpoint first and inspect the returned
capability flags.

| Feature                | Description                                                 |
| ---------------------- | ----------------------------------------------------------- |
| `streaming`            | Stream songs with range headers instead of just downloading |
| [`stations`](#station) | Use and create stations                                     |
| [`explore`](#explore)  | Home page with different sections and resources to explore  |

## Language

`lang` should use a locale string in the `BCP 47 language tag` format such as `en-US`, `de-CH`, or `ja-JP`.

OpenMusic implementations do not have to provide localized data at all.

If an implementation does support localization, `en-US` is the recommended
default locale.

If `lang` is omitted or the requested locale is unavailable, the implementation
should fall back to `en-US` when possible.

Fields like names, lyrics, descriptions, section titles, infos and so on should be localized in the requested language if possible.

## Info Endpoint

The info endpoint should be the first request a client makes.

It returns:

- branding metadata for display
- the supported OpenMusic spec version
- capability flags describing which optional families are implemented

More detail:

- [`Info`](/openmusic/info/get-api-info)

## Resources

Resource ids are preferably cuid2 or a canonical OpenMusicMetadata id.

OpenMusicMetadata ids are in the format `omm:type:cuid2` (for example: `omm:songs:oftay2u1l6i8fgpytmu6laxn`) and are used to map the same song, album, or artist across different OpenMusic implementations or the OpenMusicMetadata database.

### Song

Songs are the core required resource type.
They contain the main metadata, file information, and links to related albums,
artists, and optionally lyrics.

More detail:

- [`Songs`](/openmusic/songs/get-a-song)

### Album

Albums group songs into a release.
They usually expose shared metadata such as name, artwork, UPC, genres, release
date, and relationships to tracks and artists.

- [`Albums`](/openmusic/albums/get-an-album)

### Artist

Artists represent performers or creators.
They expose artist metadata and connect outward to songs and albums.

- [`Artists`](/openmusic/artists/get-an-artist)

### Playlist

Playlists are curated track collections.
They behave like named lists of songs with artwork, curator information, and
track relationships.

- [`Playlists`](/openmusic/playlists/get-a-playlist)

### Station

Stations are dynamic playlists generated from a seed.
In the current spec, a station can be based on an artist, a genre, or popular
tracks.

Unlike a normal playlist, the station is defined by how it is generated rather
than by a fixed curated track list.

- [`Stations`](/openmusic/stations/get-an-artist-station)

## Response Envelopes

The common wrappers used throughout the spec are:

- single resource response
- list resource response
- error response

See [`Responses`](/openmusic/responses) for the shared envelope types.
